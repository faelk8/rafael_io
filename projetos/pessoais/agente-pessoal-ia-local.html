PROJETO PESSOAL

Agente pessoal com IA local

Plataforma experimental de agentes de IA executados localmente, com orquestração própria, memória persistente e semântica, ferramentas controladas por perfil e integração com projetos reais.

Ollama Qwen2.5-Coder Python PostgreSQL pgvector Neo4j Embeddings RAG MCP NiceGUI Clean Architecture Agent Harness GPU IA local

Minha contribuição

Desenvolvo este projeto como uma plataforma experimental de agentes de IA para uso no meu próprio ambiente de desenvolvimento. A proposta não é apenas conversar com um modelo local, mas construir toda a infraestrutura necessária ao redor dele: orquestração, memória, recuperação de contexto, ferramentas, segurança, interfaces e integração com projetos.

O núcleo foi desenvolvido em Python com arquitetura própria, sem depender de frameworks como LangChain, LangGraph, CrewAI ou AutoGen. As decisões mais importantes do projeto foram registradas em ADRs para manter explícitos os motivos, alternativas avaliadas e riscos técnicos de cada escolha.

De assistente local para uma plataforma de agentes

O projeto começou a partir do interesse em executar modelos de linguagem localmente e evoluiu para uma arquitetura com múltiplos agentes especializados. Hoje existem nove perfis configurados em TOML, cada um com prompt, responsabilidades e limites próprios.

Três deles atuam como orquestradores: jota, voltado ao trabalho geral com código e ferramentas; linkedin_vagas, para consulta de vagas e acompanhamento de candidaturas; e investimentos, para análise de carteira, histórico e documentos.

Outros seis agentes são especializados em tarefas específicas: resumo, produção de conteúdo para LinkedIn, geração de docstrings, documentação Sphinx, programação Python e PostgreSQL.

Um modelo local, vários comportamentos

Os nove perfis utilizam atualmente o modelo qwen2.5-coder:7b-instruct-q4_K_M, executado localmente pelo Ollama, com temperatura 0.2 e contexto de 8192 tokens.

Em vez de depender de um modelo diferente para cada tarefa, o comportamento é definido principalmente por configuração: prompt, ferramentas permitidas, quantidade máxima de passos e contrato de saída. Isso permite experimentar especialização de agentes mantendo uma base de inferência comum.

Arquitetura de orquestração própria

O fluxo principal começa com um perfil escolhido por configuração. Antes de responder, o sistema combina memória recente, conhecimento recuperado e regras do agente. Em seguida, um serviço decisor determina se a solicitação deve ser respondida diretamente ou encaminhada para uma ferramenta.

O roteamento de ações é híbrido: regras determinísticas tratam casos explícitos e, nos demais casos, o próprio LLM retorna uma decisão estruturada em JSON. Se uma ferramenta for chamada, seu resultado volta para o contexto antes da geração da resposta final.

A arquitetura utiliza componentes próprios como AgentConfig, BaseTool, ToolManager e DecisorService, mantendo separadas as regras de negócio, configurações dos agentes e implementações concretas.

Harness: ferramentas e limites por agente

Cada perfil possui um harness definido em TOML. Ele determina quais ferramentas o agente está autorizado a utilizar e quantos passos de execução pode realizar.

Os três agentes orquestradores podem utilizar ferramentas e executar até oito passos dentro do ciclo de decisão. Os agentes especializados de texto e programação não recebem ferramentas próprias: sua responsabilidade é limitada à transformação ou análise do conteúdo fornecido.

PostgreSQL como memória durável

As conversas são persistidas no PostgreSQL, que funciona como fonte de verdade do histórico. Além das mensagens do usuário e do agente, são armazenados dados como agente utilizado, chat, assunto, data e identificadores de requisição.

Essa decisão surgiu da necessidade de preservar conversas entre reinicializações e permitir buscas e filtros. Antes de escolher PostgreSQL, considerei alternativas como JSON, SQLite e Redis.

Contexto curto sem perder o histórico

Durante uma conversa, o modelo recebe uma janela das últimas cinco mensagens individuais, combinada com um resumo acumulado do histórico anterior.

Quando mensagens deixam a janela ativa, o próprio LLM atualiza o resumo, preservando fatos, decisões, preferências e pendências. As mensagens originais continuam armazenadas no PostgreSQL; o resumo funciona como uma representação compacta do contexto anterior.

Memória semântica com embeddings e Neo4j

Para encontrar assuntos relacionados sem depender apenas de busca textual, o projeto combina embeddings locais com estruturas vetoriais e um grafo no Neo4j.

A similaridade é calculada por cosseno entre embeddings. O grafo trabalha com entidades como chats, mensagens, resumos, projetos, artefatos e conhecimentos, permitindo representar relações entre assuntos e contextos diferentes.

RAG e conhecimento de projeto

O sistema possui uma camada de recuperação de conhecimento. Soluções registradas podem ser pesquisadas com embeddings armazenados via pgvector, combinando similaridade semântica, termos e filtros por projeto ou escopo.

Até cinco resultados relevantes podem ser incorporados ao contexto antes da resposta. A indexação dos projetos é incremental, utiliza arquivos conhecidos pelo Git, ignora arquivos sensíveis e divide código Python por funções e classes.

Essa camada ainda não é um RAG completo sobre todo o código indexado, e essa limitação é tratada explicitamente no projeto.

Ferramentas próprias e segurança

Os agentes orquestradores podem executar ações além de gerar texto. Existem ferramentas próprias em Python para arquivos, terminal, análise de código e integrações externas.

O acesso a arquivos é restringido à raiz configurada e arquivos de credenciais são bloqueados. A execução no terminal utiliza shell=False, timeout, limite de saída e bloqueios para determinados comandos administrativos.

O projeto não trata essa execução como uma sandbox completa: os processos ainda herdam as permissões do processo principal, e essa limitação faz parte da arquitetura conhecida.

Integrações MCP

O projeto possui clientes MCP para integração com serviços externos como Notion e GitHub. As ferramentas são descobertas pelo servidor e chamadas pelo agente quando habilitadas pelo perfil.

Operações de escrita no GitHub exigem confirmação explícita, mantendo uma barreira adicional para ações que podem modificar recursos externos.

Clean Architecture e decisões registradas

Com o crescimento das integrações, adotei Clean Architecture e injeção de dependências para evitar que regras de negócio ficassem acopladas diretamente a PostgreSQL, Neo4j, Ollama ou outras implementações.

As principais escolhas foram formalizadas em seis ADRs: persistência do chat com PostgreSQL, memória semântica com Neo4j, inferência local com Ollama, Clean Architecture, sistema extensível de ferramentas e interface web com NiceGUI.

Interface web, terminal e IDE

A interface web foi construída com NiceGUI para manter o projeto predominantemente em Python, sem exigir um frontend separado apenas para uso local.

O sistema também pode ser utilizado pelo terminal, API e integração com IDE, aproximando os agentes do ambiente onde o desenvolvimento realmente acontece.

Observabilidade do próprio agente

O ambiente mede separadamente latência de geração textual e tempo gasto nas decisões de ação, mantendo métricas p50 e p95 das execuções recentes. Também são acompanhados consumo de RAM e VRAM.

Ainda existem pontos a evoluir: não há fallback automático entre modelos, retry geral de inferência nem histórico completo de cada tool call. Essas limitações são tratadas como oportunidades de evolução da plataforma.

Por que executar localmente

Privacidade e custo de inferência foram fatores importantes na escolha do Ollama. Conversas, contexto de projetos, embeddings e inferência podem permanecer dentro do ambiente local sem depender obrigatoriamente de APIs externas.

A execução local também torna visíveis decisões que normalmente ficam escondidas atrás de uma API: consumo de VRAM, quantização, cold start, tamanho de contexto e concorrência passam a fazer parte da arquitetura.

Um laboratório para arquitetura de IA

O valor deste projeto está menos em criar mais uma interface de chat e mais em experimentar os componentes necessários para que agentes sejam realmente úteis: memória, contexto, recuperação, ferramentas, permissões, arquitetura de software e observabilidade.

Ele funciona como meu laboratório para estudar como modelos de linguagem podem participar de atividades reais de desenvolvimento mantendo controle sobre os dados, as ferramentas disponíveis e as decisões tomadas pelo sistema.
